# EP 91. 26.1Q 비즈니스 관점에서의 AI

## 원문
- YouTube: https://youtu.be/FPYOVt2B5EM?si=3SH_WB6b6ArChEtj
- 전사본: https://aifrontier.kr/ko/episodes/ep91/
- 발표자료: https://aifrontier.kr/episodes/ep91/slides.pdf

## 한줄 요약
AI의 본질은 점점 더 많은 문제를 **compute 기반 search problem**으로 바꾸는 것이고, 비즈니스의 핵심 경쟁은 기존 UX와 앱을 유지하는 것이 아니라 **개인 에이전트·하네스·평가 루프를 중심으로 업무와 산업을 재구성하는 것**으로 이동하고 있다는 주장.

## 핵심 포인트 요약
### 1. OpenClaw와 하네스는 단순 도구가 아니라 새로운 업무 운영 레이어
- OpenClaw Seoul 밋업 사례를 통해, 여러 AI 하네스와 메타 레이어 구조가 실제 업무 흐름을 분업·자동화하는 형태로 발전하고 있다고 설명.
- 사람은 목표와 방향을 주고, 하위 에이전트/하네스가 cascade 식으로 실행하고 다시 리포트하는 구조가 강조됨.
- 하네스는 일종의 작은 AI 회사처럼 설계될 수 있으며, 안정된 부분은 자동화 루프로 넘길 수 있다는 관점.

### 2. AI의 본질은 문제를 search / optimization 구조로 바꾸는 것
- RLVR(Reinforcement Learning by Verifiable Rewards), CUA(Computer Use Agent), auto research, Ralph loop 등을 같은 구조로 묶어 설명.
- 핵심은 **문제를 검증 가능한 보상 구조로 바꾸고**, compute를 투입해 탐색과 최적화를 반복하는 것.
- 목표(objective)와 평가 기준(evaluation metric)이 명확해질수록 AI가 문제를 더 강하게 풀 수 있다는 프레임.

### 3. 모델은 우리 생각보다 이미 훨씬 강하고, capability overhang이 크다
- GPT-5.4 수준은 실무에서 크게 실망하지 않을 정도로 안정적이라고 평가.
- “특정 도메인용 하네스”보다 강한 범용 모델 + 적절한 루프와 평가 구조가 더 중요하다는 관점 제시.
- 지금 안 풀리는 문제도 모델 개선 주기(6개월~1년) 안에서 풀릴 가능성이 높다는 태도.

### 4. 비즈니스는 기존 앱/서비스 자체보다 ‘에이전트가 조작하는 레이어’로 재편될 수 있다
- OpenClaw류 개인 에이전트가 최상단 인터페이스가 되면, 기존 앱은 에이전트가 대신 조작하는 하위 레이어로 내려갈 수 있다는 주장.
- 배달앱, 커머스앱, 택시앱 등은 사용자가 직접 들어가는 목적지가 아니라 에이전트가 function call 또는 CUA로 이용하는 대상이 될 수 있음.
- 이 과정은 기존 게이트키퍼의 friction과 마진 구조를 깨는 방향으로 작동할 가능성이 큼.

### 5. Bundle / Unbundle 관점이 중요
- 새로운 distribution layer가 열릴 때마다 산업은 bundle → unbundle → rebundle의 반복을 겪음.
- AI 시대는 기존 SaaS, 앱, UX가 다시 unbundle되는 시기이며, 개인 에이전트가 새로운 분배 채널이 될 수 있다는 시각.
- ChatGPT/Claude/Gemini 같은 거대 서비스가 최종 승자가 아닐 수 있고, 오히려 개인화된 에이전트들이 상단 접점을 차지할 가능성이 제시됨.

### 6. 기업의 AX는 ‘효율화’만으로 끝나면 한계가 있다
- 업무 일부를 도와주는 수준의 AX는 조직 인센티브와 충돌해 실제 생산성 향상으로 이어지지 않을 수 있음.
- 진짜 AX는 특정 업무를 조금 도와주는 것이 아니라, **업무 단위를 통째로 없애고 사람을 더 상위 역할로 재배치하는 수준**이어야 한다는 주장.
- 동시에 효율 개선(1/10x)과 신사업 창출(10x new biz)은 서로 다른 성격의 문제이며, 후자는 entrepreneur형 리더가 필요하다고 봄.

### 7. 돌고 돌아 ‘순정 바닐라’에 가까운 운영이 강해질 수 있다
- 지나치게 복잡한 자체 프레임워크보다:
  - 데이터 커넥터를 잘 만들고
  - 프롬프트를 잘 쓰고
  - frontier 모델 + 검증 루프를 잘 붙이는 것
  이 더 강력할 수 있다는 실전적 결론.
- 즉, bespoke system을 과도하게 만들기보다 **좋은 모델 + 명확한 평가 구조 + 데이터 연결성**이 핵심이라는 메시지.

### 8. 보안과 프롬프트 인젝션 문제는 여전히 매우 현실적
- OpenClaw 같은 자율 에이전트는 능력이 커질수록 보안 리스크도 커짐.
- 실제 운영은 VM/격리 환경/제한된 credential/낮은 위험 작업 위주로 시작하는 게 합리적이라는 경험적 조언이 제시됨.

## 더 알아보면 좋은 부분 (딥리서치 확장 포인트)
### A. RLVR / Verifiable Rewards가 실제 비즈니스 문제에 어디까지 적용되는가
추가로 파볼 주제:
- 비코딩 업무에서 검증 가능한 평가 기준을 만드는 방법
- 마케팅, 리서치, 지식관리, 투자 아이디어 발굴을 verifiable loop로 바꾸는 사례
- reward hacking을 줄이는 평가 설계 방식

### B. 개인 에이전트가 앱을 unbundle하는 시나리오의 현실성
추가로 파볼 주제:
- 현재 CUA 기반 앱 자동화의 한계
- 모바일 환경에서 개인 에이전트가 상단 게이트웨이가 될 가능성
- 기존 플랫폼들이 agent scraping / agent access를 어떻게 대응할지

### C. AX에서 효율화와 신사업 창출을 분리해 보는 프레임
추가로 파볼 주제:
- 1/10x 효율화 사례 vs 10x 신사업 사례 비교
- 기업 내부 AI 도입이 실패하는 조직 인센티브 문제
- AI native talent와 기존 조직 간 역할 재편 모델

### D. 보안 운영 원칙
추가로 파볼 주제:
- OpenClaw/에이전트형 시스템의 최소 권한 원칙
- prompt injection 대응 패턴
- credential 분리, VM 격리, 샌드박스 전략

## 냐안의별에게 적용할 부분
### 1. 옵시디안 워크플로도 search / loop 구조로 설계할 수 있음
이 영상의 핵심 논리는 네 워크플로에도 잘 맞음.
- 링크를 받는다
- 원문/스크립트 확보
- 핵심 요약 생성
- 추가 조사 질문 생성
- 관련 허브 노트에 연결
- 나중에 재사용하며 평가/보완
이 흐름 자체가 하나의 지식 하네스가 될 수 있음.

### 2. 지나친 커스텀 시스템보다 ‘좋은 모델 + 좋은 구조’가 우선
현재 네 옵시디안 운영도:
- 데이터 커넥터(링크 수집 경로)
- 프롬프트 규칙(어떻게 요약/딥리서치할지)
- 저장 템플릿
- 허브 노트 연결
이 4개가 잘 잡히면 매우 강해질 가능성이 큼.

### 3. OpenClaw를 중심으로 개인 에이전트형 지식 시스템을 만드는 방향성과도 잘 맞음
이 영상은 네가 원하는 방향, 즉:
- 여러 봇 결과 수집
- 옵시디안 저장
- 필요할 때 재활용
- 하네스화/에이전트화
와 상당히 잘 맞닿아 있음.

## 투자 참고 포인트
### 주목 포인트
- AI 경쟁의 승부가 단순 모델 성능이 아니라 **모델 + 하네스 + RL 환경 + distribution layer**의 조합으로 이동 중이라는 관점은 중요함.
- 기존 앱/플랫폼이 agent layer 아래로 내려갈 가능성은 플랫폼 기업, SaaS, 검색/커머스/배달/중개 업종을 보는 데 참고할 만함.
- compute cost 하락, 오픈 레시피 확산, 모델 commoditization 가능성은 인프라/오픈소스/에이전트 툴링의 상대적 가치 재평가 포인트가 될 수 있음.

### 확인이 더 필요한 부분
- 실제로 개인 에이전트가 대중적 상단 인터페이스가 되기까지의 시간표
- 플랫폼 사업자들이 API 정책, anti-bot 정책, 인증 장치로 얼마나 방어 가능한지
- 에이전트 보안 사고가 adoption 곡선을 얼마나 늦출지

## 내가 주목한 문장형 결론
- 모든 문제는 점점 더 compute 기반 search problem으로 환원된다.
- 인간의 역할은 execution보다 objective / taste / initiation / judgment 쪽으로 이동한다.
- AX는 일부 업무를 덜어주는 수준이 아니라, 업무 구조를 다시 짜는 수준에서 봐야 한다.
- 복잡한 자체 프레임워크보다도 frontier model + clean data connector + good prompting이 더 강할 수 있다.
- 개인 에이전트는 향후 앱 위의 상단 인터페이스가 될 가능성이 있다.
